# Ideation — 검색 품질 개선 (디스크 1.33GB 대비 검색 기여 텍스트 ~1% 문제 해소)

## 1. 배경 (사전 조사 결과 — 2026-06-12 진단 확정)

| 측정 항목 | 실측값 | 문제 |
|---|---|---|
| 라이브러리 총량 | 1,330 MB (20셀) | — |
| 검색 미연결 데이터 | XBRL 557 + source 279 + PDF 114 = **950 MB (71%)** | 저장만 됨 |
| 인덱스(index*.json) | 376 MB | **91.5%가 임베딩 벡터(JSON float 텍스트)** |
| 검색 가능 텍스트 | **~15 MB (전체의 ~1%)** | 청크 샘플링 상한 |
| PDF 커버리지 | 주석 섹션만(페이지의 ~25–35%) | MD&A·재무제표 본문 제외 |
| 임베딩 잘림 | 청크 450자 vs 모델 max_seq_length **128토큰**(실측: `src\models\ko-sroberta\sentence_bert_config.json`) | 청크 뒷부분 ~절반 미반영 |
| 결과 컷 | top-k=5 하드캡, MIN_MATCH_SCORE=0.45, 청크 max-only 스코어 | 후보 손실 |

## 2. 구현 방안 비교

| 접근 | 내용 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| **A. 파라미터 튜닝만** | top-k/임계치/가중치 조정 | 재인덱싱 불필요, 즉효 | 근본(잘림·샘플링·커버리지) 미해결 | 1단계로 채택 |
| **B. 인덱스 재설계(채택)** | 청크 정합(250자)+상한 완화+벡터 저장 최적화+스코어 개선 | 잘림 해소·커버리지 2–3배·인덱스 용량 통제 | 전체 재인덱싱 1회(셀당 1–3분×20) | **본 계획 핵심** |
| C. 외부 검색엔진 도입(FAISS/Qdrant 등) | 벡터 DB 교체 | 대용량 확장성 | 폐쇄망 동봉·PyInstaller 패키징 복잡도↑, 현 규모(수천 노트)에 과함 | 보류 |
| D. 더 큰 임베딩 모델 교체 | bge-m3 등(8k 토큰) | 장문 임베딩 | 모델 2GB+, 번들 비대, 재검증 비용 | 보류(차기) |

## 3. 제약사항 & 극복
- **폐쇄망 데모**: 외부 다운로드 0 — 기존 동봉 ko-sroberta 유지(D안 배제 근거). Ollama(qwen2.5:7b)는 데모 PC 설치 전제일 때만 리랭킹 활성(없으면 자동 OFF — 기존 패턴).
- **인덱스 비대 위험**: 청크 상한 완화 시 376MB→1GB+ 우려 → **벡터 소수점 5자리 반올림(JSON 크기 ~45%↓) + 청크 250자(벡터 수↑ 상쇄)**로 통제. 목표: 셀당 ≤25MB.
- **Windows/PyInstaller**: 신규 의존성 없음(numpy/rank_bm25/kiwipiepy 기존 유지).
- **언어 선정**: Python 유지 — 기존 스택(FastAPI·numpy·fitz), 데이터 처리 영역, 추가 검토 불필요.

## 4. 단계별 계획

### Phase 0 — 평가 하네스 (개선을 "증명"할 기준)  [선행 필수]
- 골든 질의셋 `tests\golden_queries.json`: 실무 질의 20개 × 기대 주석(회사·기간·노트번호) 수작업 라벨.
- 평가 스크립트 `src\eval_search.py`: Recall@5/@10, MRR 산출. pytest 비차단(별도 실행).
- **산출물**: 개선 전 베이스라인 수치 → 각 Phase 후 재측정.

### Phase 1 — 검색 단 개선 (재인덱싱 불필요, 즉효)
1. `rank_notes_for_query` k=5→**10**(env `SEARCH_TOP_K`), `MIN_MATCH_SCORE` 0.45→**0.35** + UI 신뢰도 배지(high/low 기존 필드 활용).
2. `_note_unit_cos`: max-only → **max 0.6 + 상위3 청크 평균 0.4** 혼합(다중 청크 매칭 가산).
3. BM25: 제목 코퍼스/청크 코퍼스 **분리 산출 후 가중 결합**(제목 0.5 + 청크 0.5) — 제목 고신호 토큰 희석 해소.
- 예상: Recall@10 +15–25%p (재인덱싱 없이).

### Phase 2 — 인덱스 재설계 (1회 전체 재인덱싱)
4. `CHUNK_CHARS` 450→**250**, `CHUNK_OVERLAP` 80→50 — 모델 128토큰 정합(잘림 해소).
5. `CHUNK_SCAN_PAGE_CAP` 20→**노트 전체 범위**, `MAX_CHUNKS_PER_NOTE` 40→**120**, `MAX_CHUNKS_PER_PAGE` 3→4 — 장문 주석 커버.
6. 임베딩 저장: `round(x, 5)` 반올림(JSON 크기 ~45%↓, 코사인 오차 무시 가능) + 스키마 v3 태깅. (선택: `embeddings.npy` 사이드카 분리 — 효과 크면 차기)
7. 노트 **본문 전문**(`full_text`) 저장 — 검색 스니펫·RAG 컨텍스트 품질 향상(텍스트는 셀당 ~2–5MB로 저렴).
8. 일괄 재인덱싱 스크립트 `src\reindex_all.py`(기존 index_entry 루프) + 진행 로그.
- 예상: 검색 가능 텍스트 15MB→40–60MB(3–4배), 잘림 0건. 인덱스 크기 ≈ 현 수준 유지(반올림 상쇄).

### Phase 3 — 커버리지 확장 (주석 밖 콘텐츠)
9. **섹션 인덱싱**: 재무제표 본표·MD&A를 목차 휴리스틱(슬림: 키워드, full: 페이지 레이아웃)으로 섹션 단위 추출 → `doc_section` 축 추가(주석과 구분되는 note_kind="섹션"). UI 필터 토글.
10. **XBRL 크로스링크**: fs_structured 계정명 ↔ 주석 제목 임베딩 매칭(오프라인 1회) → 검색 결과 카드에 "관련 재무수치" 보강 표시.
- 예상: PDF 커버리지 35%→70%+, 수치 질의 응답력 확보.

### Phase 4 — 랭킹 고도화 (선택, Ollama 가용 시)
11. LLM 리랭킹: 상위 20 후보(제목+첫 청크)를 qwen2.5:7b로 재정렬(타임아웃 3s, 실패 시 무시 — 기존 보정 패턴 재사용).

## 5. 일정/검증
| Phase | 작업량(추정) | 검증 |
|---|---|---|
| 0 | 0.5일 | 베이스라인 Recall/MRR 산출 |
| 1 | 0.5일 | 단위테스트(스코어 혼합·k/임계치) + 골든셋 재측정 |
| 2 | 1일 + 재인덱싱 ~1h | 스키마 v3 단위테스트, 잘림 0 확인(토큰 길이 검사), 골든셋 재측정, 셀당 크기 ≤25MB |
| 3 | 1.5–2일 | 섹션 추출 단위테스트, 커버리지 리포트 |
| 4 | 0.5일 | 리랭킹 on/off A/B 골든셋 비교 |

- 버전: Phase 1–2 완료 시 MINOR(0.3.0 계열), 스키마 v3 하위호환(v2 인덱스 읽기 유지, 재인덱싱 권장 안내).
- 빌드: 폐쇄망 exe 재빌드는 Phase 2 완료 후 1회.

## 5b. 인덱스 이식(포터블) — GPU 없는 PC에서 재활용 방안

### 핵심 원리 (실측 확인)
- **검색 시 GPU 불필요**: 무거운 연산은 인덱싱(노트·청크 수백 건 임베딩)뿐.
  검색은 질의 1문장 임베딩(CPU 50–300ms) + numpy 코사인 — 동봉 torch CPU로 충분.
- **셀 폴더 자기완결 확인**: catalog.json·index*.json 모두 **절대경로 0건**(실측) —
  `library\{회사}\{기간}\` 폴더 복사만으로 이식 가능.
- **유일한 등록부**: `storage\catalog.json`(매트릭스 표시 근거)은 library 밖 단일 파일 —
  미반입 시 셀이 디스크에 있어도 화면에 안 나옴 → 재구성 장치 필요(아래 B-2).

### 방안 비교
| 방안 | 내용 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| **A. 폴더 반출/반입(절차)** | 인덱싱 PC에서 일괄 인덱싱 → `storage\` 통째 zip → 폐쇄망 반입 → exe 옆 `storage\` 교체 | 코드 0줄, 현행 빌드 동봉 방식과 동일 | 부분 병합 불가(통째 교체), catalog 수동 관리 | **즉시 운영 가능(기본)** |
| **B. 앱 내 내보내기/가져오기(채택)** | ①셀 선택 zip 내보내기 API+버튼 ②zip 가져오기(검증+병합) ③catalog 재구성(rescan) | 부분 병합·검증 자동, 비개발자 운영 가능 | 0.5–1일 개발 | **기능화 권장** |
| C. CPU 인덱싱 가속(ONNX int8) | onnxruntime 양자화로 CPU 인덱싱 2–4배 | GPU 없는 PC에서도 직접 인덱싱 현실화 | 의존성·패키징 추가, 정확도 재검증 | 차기 보류 |

### B안 설계
1. **내보내기**: `GET /api/library/export?cells=신한/2025Q3,...` → zip(셀 폴더들 + manifest.json).
   manifest: 스키마 버전, 임베딩 차원(768), 모델명(ko-sroberta), 생성일 — 가져오기 검증용.
2. **가져오기**: `POST /api/library/import` (zip 업로드) →
   - 검증: manifest 차원=현재 백엔드 차원(기존 EMBED_DIM 가드 재사용), 스키마 호환, zip 경로 탈출 차단(`..` 금지 — 기존 보안 규칙).
   - 병합: 셀 단위 복사(동일 셀 존재 시 덮어쓰기 확인), `upsert_catalog_entry` 로 카탈로그 자동 등록.
3. **catalog 재구성**: `POST /api/library/rescan` — library 디스크 스캔(meta.json+index* 존재 기준)으로
   카탈로그 재생성. A안(통째 복사)·수동 폴더 작업 후 복구 용도.
4. UI: 자료추가 모달에 "내보내기/가져오기" 서브탭 또는 매트릭스 상단 버튼.

### 운영 시나리오(폐쇄망 데모)
1. 사내 인덱싱 PC(망연결·GPU 무관)에서 DART 수집 + Phase 2 재인덱싱 일괄 수행.
2. 내보내기 zip(인덱스 포함, XBRL/source 제외 옵션 — 반입 용량 1.3GB→약 0.5GB 절감) 반입.
3. 데모 PC(GPU 無): 가져오기 → 차원 검증 통과 → 즉시 검색 가능(인덱싱 0회).
4. 데모 중 신규 분기 필요 시: CPU 인덱싱도 가능(셀당 수 분) — 사전 안내.

### 주의/가드
- 모델 불일치 반입(예: bigram 512 환경) → 기존 503 차원 가드가 검색 시 안내하나,
  **가져오기 시점에 선제 차단**(manifest 검증)이 B안의 핵심 가치.
- PDF 동반 여부 선택: 검색만이면 index*만으로 동작하나 뷰어(원문 표시)는 PDF 필요 — 기본 포함 권장.

## 6. 리스크
- 임계치 완화로 저신뢰 결과 노출 증가 → UI 신뢰도 배지·정렬로 완화.
- 재인덱싱 중 서비스 중단 → 셀 단위 순차 처리(기존 INDEX_STATUS 진행 표시 재사용).
- 섹션 휴리스틱 오탐 → note_kind 분리로 주석 검색 본선에 영향 차단.
