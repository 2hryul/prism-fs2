# Ideation — 라이브러리 화면 사업보고서 처리 재도입

> 2026-06-19 08:21 · 대상 repo: prism-fs (`main` `b98b8d3`) · 결정: 현 prism-fs에 사업보고서(report) 재도입

## 1. 배경·목표
- v0.4.0(`c6f4c87`)에서 사업보고서(report) doc_type을 전면 제거(당시 `VALID_DOC_TYPES`: `report`/`review`/`review_sep` → `review`/`review_sep`).
- 이번 요청: **라이브러리 화면부터** 사업보고서를 다시 처리(업로드·인덱싱·검색·비교)할 수 있도록 수정.
- 핵심: 단순 git revert가 아니라, 제거 이후 성숙한 **현행 아키텍처**(본문 전체 인덱싱 `build_body_index`, 문장경계 청크 schema4, `cell_keys` 선택검색, 주석 우선 정렬 S1)에 `report`를 **3번째 doc_type**으로 일관 이식.

## 2. 사업보고서 문서 특성 (review류와 차이)
| 항목 | 검토보고서(review/review_sep) | 사업보고서(report) |
|---|---|---|
| 구성 | 재무제표 주석 중심 | **본문(사업현황·MD&A 등) + 재무제표 + 주석** |
| fs_div | 연결/별도로 명확 | **연결·별도 혼재(중립)** → fs_div "all" 처리 |
| 분량 | 중 | 대(수백 페이지) |
| 검색 단위 | 주석(footnote) + 본문유닛 | **본문유닛(`B…`) 비중 큼** + 주석 |

→ 현행 `build_body_index`(전 페이지 본문 유닛화)가 사업보고서 본문에 **그대로 최적**. fs_div 중립이라 report는 fs_div 필터 우회(`all`) 필요.

## 3. 구현 방안 비교

### 방안 A — 현행 doc_type 모델에 `report` 추가 (★권장)
- 백엔드: `VALID_DOC_TYPES`에 `report` 추가, `pdf_path`(report.pdf)·`index_path`(index_report.json)·`body_index_path`·`_filename_matches_doc_type`·`detect_doc_type_from_text`·`_strip_doc_fields`·카탈로그 필드(`report_indexed`/`report_notes_count`/`report_collected`) 확장. `notes_rag_query`에서 report는 fs_div="all" 강제.
- 프런트: 상수(`DOC_ICON`/`DOC_FULL`/`DOC_SHORT`/`DOC_FSDIV`/인덱싱 플래그)와 선택 UI(프리셋·업로드 드롭다운·자료추가 체크박스·매트릭스 pill)에 report 추가.
- 장점: 기존 패턴 그대로 확장 → 본문 인덱싱·cell_keys·S1 검색 **전부 재활용**. 비교·검색 UX 무료 계승.
- 단점: 손대는 지점이 많음(백/프런트 doc_type 배선 일관 수정 필요).

### 방안 B — 사업보고서 전용 화면/탭 신설
- 라이브러리와 별개 탭에서 report만 관리.
- 장점: 기존 2-doc_type UI 무변경.
- 단점: 사용자 흐름 분절, 비교/검색 코드 중복, "라이브러리 화면부터" 요구와 불일치. **비권장**.

### 방안 C — git revert(c6f4c87 부분 복원)
- 옛 report 코드(`sections.py` 141줄 등) 되살림.
- 단점: 현행 본문 인덱싱·schema4·doc_type 모델과 충돌, 회귀 위험 큼. **비권장**.

## 4. 제약사항·극복
| 제약 | 극복 |
|---|---|
| doc_type 배선이 백/프런트 다지점 분산 | 그렙으로 review_sep 패턴 전수 → report 동반 추가(누락 방지 체크리스트화) |
| report는 fs_div 중립(연결/별도 아님) | `DOC_FSDIV.report = "all"`, `notes_rag_query`에서 report 셀은 fs_div 필터 우회 |
| 사업보고서 대용량 → 인덱싱 시간·셋업 번들 증가 | 본문 인덱싱 페이지 상한·청크 상한 기존값 적용, 번들은 데모셀만 |
| 하위호환(기존 16셀 review/review_sep 무영향) | report는 **순수 추가**(기존 필드·기본값 불변), report 미보유 셀은 종전과 동일 |
| 폐쇄망·결정론 | report 본문도 RAG 정성 텍스트 전용·인용 강제·숫자 무생성 유지 |

## 5. 언어 선정
- 기존 스택 유지: **백엔드 Python(FastAPI)** + **단일 `static/index.html`(JS 인라인)**. 신규 언어 도입 없음.
- 근거: doc_type 모델·인덱싱·검색이 모두 현 스택에 구현됨. Windows 11 빌드·PyInstaller 번들 검증 완료. 별도 언어는 불필요한 복잡도.

## 6. 추천: 방안 A
현행 패턴 확장으로 본문 인덱싱·검색(S1)·비교 UX를 그대로 계승하면서 사업보고서를 3번째 문서유형으로 추가. 다음 단계: EARS 스펙 작성 → 백엔드 doc_type 확장 → 프런트 UI 확장 → 업로드/인덱싱/검색 수동·단위 테스트.
